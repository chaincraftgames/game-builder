# Mechanics Wishlist

Mechanics are named engine-understood patterns that the LLM configures rather than
hand-implementing. Each mechanic is **generative** — it synthesizes action slots,
inventory slots, preconditions, effects, and/or win conditions from a compact
declaration. The engine knows how to execute each `kind`; the spec only provides
config values.

## Ownership principle
- If a mechanic requires an inventory and nothing else in the spec needs to reference
  it directly, the **mechanic owns and injects it** (not declared in inventories module).
- If other modules (effects, flow, actions) reference the inventory by ID, it stays
  in the inventories module and the mechanic takes an ID reference.

## Scopes
- **Piece-level**: declared in `mechanics[]` on a `GamepieceType`. Affects a single piece
  type — injects action slots, piece-scoped inventory slots, preconditions.
- **Game-level**: declared in a top-level `mechanics[]` on the game spec. Affects game
  structure — injects scoring, elimination, trading rules, etc.

## Piece-level mechanics

### `chaincraft:charges`
**Status**: Schema written (`mechanics/charges.ts`)

Gates an action behind a charge cost drawn from a piece's own inventory.

Key config:
- `slotId` — namespaced action slot ID generated by this mechanic
- `chargeType` — gamepiece type for charge tokens (mechanic owns unless referenced elsewhere)
- `maxCharges` — capacity of the injected piece-scoped charge inventory
- `count` — tokens consumed per activation
- `action` — action ID from the actions module to execute
- `depleteTo` — where spent tokens go (default `game:unassigned`)
- `availableInSubflows` — flow node IDs where slot is active

Synthesizes: piece-scoped charge inventory, precondition, slot, post-action cleanup.

Examples: energy counters, exhaustion/tap mechanic, potion charges, ammo.

---

### `chaincraft:conversion`
**Status**: Schema to be written (`mechanics/conversion.ts`)

Spend one or more resource inventories to produce one or more resource inventories.
Supports many-to-many conversions (e.g. 2 ore + 1 coal → 1 steel + 1 ash).

Key config:
- `slotId` — namespaced action slot ID generated by this mechanic
- `sources[]` — `{ inventory, count }` inputs consumed on activation
- `targets[]` — `{ inventory, count }` outputs produced on activation
- `availableInSubflows`

Synthesizes: slot, source preconditions, drain effects, fill effects.
All inventories are piece-scoped and referenced by ID (declared in inventorySlots[]
on the piece type, or owned by this mechanic if exclusive to it).

Examples: ore smelter, alchemy, crafting bench, trade route.

### `chaincraft:npc-behavior`
**Status**: Not yet designed

Scripted, game-controlled behavior for a gamepiece (monster, enemy, NPC). Fires
automatically when a named trigger effect executes — no player choice involved.
Selects a behavior from a weighted list, respecting per-behavior cooldowns. The
selected behavior's effects fire against a target (typically the acting player).

Key config (tentative):
- `trigger` — named effect ID that initiates the NPC's turn (e.g. `resolve-monster-turn`,
  called from a player turn's `onComplete` hook)
- `target` — who the NPC acts against: `trigger-actor` (the player whose hook fired) |
  `all-players` | `{ roles: [...] }`
- `behaviors[]` — ordered list of possible behaviors:
  - `id` — behavior identifier (also used as cooldown property name)
  - `weight` — relative probability weight (engine sums all weights, rolls, picks proportionally)
  - `cooldown` — number of triggers this behavior is unavailable after use (0 = no cooldown)
  - `fallback` — if `true`, this behavior is used whenever the rolled behavior is on cooldown
  - `effects` — inline effect list to execute when this behavior is selected

Engine behavior:
1. Sums weights of all non-cooldown behaviors, rolls
2. If the selected behavior is on cooldown, finds the nearest `fallback: true` behavior
3. Fires selected behavior's effects (target resolved at runtime)
4. Decrements all active cooldowns; sets used behavior's cooldown counter
5. Engine auto-injects a cooldown property per behavior onto the piece type

Notes:
- Purely reactive NPC responses (taking damage → counter) are better modeled as
  passives on the piece type (already supported). `npc-behavior` is for *proactive*
  NPC actions initiated on a trigger.
- Spatial/AI behavior (pathfinding, chase logic, adjacency targeting) exceeds what any
  structured mechanic can express — use `kind: custom` effects for those.
- Cooldown is tracked per piece instance, so a game with multiple monster instances
  tracks cooldowns independently per piece.

Examples: Munchkin monster attacks (weighted randoms + cooldown on strong attack),
dungeon crawler enemy turns, solo game AI opponents.

## Game-level mechanics

### `chaincraft:score-track`
**Status**: Schema to be written (`mechanics/score-track.ts`)

Tracks player or team scores on a line-structure board. Mechanic owns the track
inventory and marker piece type — neither needs to be declared in inventories or
gamepiece-types modules.

Key config:
- `id` — mechanic instance ID (needed if game has multiple tracks)
- `trackLength` — number of positions on the line inventory
- `markerType` — mechanic-owned gamepiece type for score markers (one per player/team)
- `scoringProperty` — player/team property to keep in sync with marker position
- `scope` — `player` | `team` (one marker per player or per team)
- `winAt` — optional: auto-wire an endCondition to the root flow loop
- `finalRound` — if winAt set: complete current iteration before exiting

Synthesizes: line inventory, marker type, `advance` effect (callable from actions/hooks),
optional endCondition wired into flow.

Notes:
- Score track behavior (advancing, score-track mechanic) is separate from the line
  inventory structure. The line inventory is structural; the mechanic adds the behavior.
- If the game needs players to see the track visually, the mechanic creates a
  `game`-scoped line inventory (not `game:unassigned`).

Examples: Catan victory points, Ticket to Ride score track, Wingspan egg track.

### `chaincraft:dominant-gamepiece`
**Status**: Schema to be written (`mechanics/dominant-gamepiece.ts`)

Evaluates dominant suit in trick-taking games. The mechanic references an existing
inventory (must be declared in inventories module) because flow conditions and
actions also reference it.

Key config:
- `suitProperty` — property on card pieces that holds the suit value
- `rankProperty` — property on card pieces that holds the rank/value
- `dominantSuit` — literal suit string OR a JsonLogic expression (e.g. `{ var: "game.property.dominantSuit" }`)
- `evaluationInventory` — inventory ID containing the cards being evaluated (trick pile)

Synthesizes: comparison logic for trick resolution, exposes a `resolve-trick` effect.

Notes:
- Dominant suit can be dynamic (set by a bid or by cutting the deck) — use JsonLogic var.
- No-dominant mode: omit `dominantSuit` or set to `null`.

Examples: Hearts (no dominant), Spades (spades always dominant), Euchre (declared dominant),
Bridge (bid determines dominant).

### `chaincraft:elimination`
**Status**: Not yet designed in detail

Removes players from the game when an elimination condition is met.

Key config (tentative):
- `condition` — JsonLogic expression evaluated per-player (e.g. health reaches 0)
- `trigger` — when to evaluate: `turn-end` | `round-end` | `on-change`
- `eliminatedProperty` — player property to set on elimination (for flow conditions)
- `finalRound` — whether remaining players get one more turn after elimination fires

Synthesizes: per-player condition check wired to trigger timing, elimination side-effect.

Notes:
- "Last player standing" end condition is a separate flow endCondition referencing
  the eliminatedProperty count.

Examples: Liar's Dice (lose all dice → eliminated), King of Tokyo, Coup.

### `chaincraft:trading`
**Status**: Not yet designed in detail

Player-to-player resource exchange, optionally with negotiation.

Key config (tentative):
- `tradableInventories[]` — inventory IDs that can be included in trades
- `requireBothAccept` — whether the recipient must accept (true = negotiated trade)
- `availableInSubflows` — flow node IDs where trading is allowed

Synthesizes: propose-trade action, accept/reject actions (if negotiated),
validation that proposer has offered resources.

Notes:
- Negotiation is modeled as a `simultaneous` node with `endCondition: "all-passed"`
  in flow — the trading mechanic may auto-wire this or reference an existing node.
- One-sided trading (gift / tribute) sets `requireBothAccept: false`.

Examples: Catan (negotiated trading), Chinatown (free trading phase), Diplomacy.

### `chaincraft:auction`
**Status**: Not yet designed

Players bid on items; highest bid wins.

Key config (tentative):
- `biddingInventory` — currency inventory used for bids
- `auctionInventory` — what's being auctioned (item pool)
- `style` — `english` (ascending open) | `dutch` (descending) | `sealed` (simultaneous)
- `winnerAction` — what happens to the winner's bid (pay bank, pay other players)

Notes:
- Dutch auction and sealed bid map naturally onto `simultaneous` flow nodes.
- English auction requires multiple bid rounds — flow loop with interrupt windows.

Examples: Power Grid, Modern Art, Ra, For Sale.

### `chaincraft:deck-building`
**Status**: Not yet designed

Players acquire cards to their personal deck during play.

Key config (tentative):
- `marketInventory` — the shared supply of acquirable cards
- `deckInventory` — player's personal draw deck (player-scoped)
- `discardInventory` — player's personal discard pile (player-scoped)
- `acquireAction` — action ID for acquiring a card to discard pile
- `autoShuffle` — reshuffle discard into deck when deck is empty (can delegate to `chaincraft:draw-discard`)

Synthesizes: reshuffle trigger, draw mechanic, standard deck-building lifecycle.

Examples: Dominion, Clank!, Star Realms, Legendary.

### `chaincraft:draw-discard`
**Status**: Not yet designed

A draw pile + discard pile pair with automatic reshuffle when the draw pile is exhausted.
When a draw is attempted and the draw pile is empty, the engine automatically shuffles
the discard pile into a new draw pile, clears the discard pile, and then completes the draw.

Mechanic OWNS both the draw and discard pile inventories (both stack-structure).
No other module needs to reference them directly — the mechanic exposes a `draw` effect
callable from actions and flow hooks.

Key config (tentative):
- `cardType` — gamepiece type ID for cards in this deck (forward ref to gamepiece-types)
- `scope` — `game` (shared deck) | `player` (each player has their own draw/discard pair)
- `reshuffleOn` — `empty` (default, reshuffle when draw pile runs out) | `low-water` (proactive,
  reshuffle before draw if pile count < `reshuffleThreshold`) | `manual` (explicit trigger only)
- `reshuffleThreshold` — minimum card count that triggers a proactive reshuffle when
  `reshuffleOn: low-water`. E.g. `5` means "if fewer than 5 cards remain, reshuffle before drawing".
  Required when `reshuffleOn: low-water`, ignored otherwise.
- `revealDiscard` — whether the discard pile's top card is visible to all players (default true)

Synthesizes:
- draw pile inventory (stack, scope-matched, owned by mechanic)
- discard pile inventory (stack, scope-matched, owned by mechanic)
- `draw` effect: draw N cards; auto-reshuffles if draw pile runs out mid-draw
- `discard` effect: move specified card(s) to top of discard pile
- reshuffle trigger: wired automatically when `reshuffleOn: empty`

Notes:
- This is a standalone mechanic useful in any game with a draw/discard cycle — not
  just deck-builders. Deck-building can delegate its reshuffle behavior to this mechanic.
- `scope: player` handles personal draw/discard piles (deck-builders).
- `scope: game` handles shared draw decks (card games like Go Fish, Rummy, standard decks).
- If players need to see how many cards are in the draw pile, mechanic sets visibility
  to `count-only` on the draw pile inventory.

Examples: Any card game (standard 52-card deck), Dominion (personal deck), Solitaire.

### `chaincraft:drafting`
**Status**: Not yet designed

Players are each dealt a hand of cards, pick one (or more), then pass the remainder
to an adjacent player. Repeat until all cards are picked or hands are exhausted.  

Key config (tentative):
- `cardType` — gamepiece type being drafted (forward ref to gamepiece-types)
- `handSize` — number of cards dealt to each player at the start of each draft round
- `picksPerPass` — number of cards each player keeps before passing (default 1)
- `passDirection` — `clockwise` | `counter-clockwise` | `alternating` (alternates each draft round)
- `draftTo` — inventory ID where picked cards go (player-scoped; must be in inventories module
  if actions/flow also reference it, otherwise mechanic can own it)
- `rounds` — number of complete draft rotations (default: until hands empty)

Synthesizes:
- deal action (setup: distribute `handSize` cards per player from a source inventory)
- pick action: player selects `picksPerPass` cards from their current hand
- pass trigger: after pick, remaining hand moves to next player in pass direction
- loop structure: repeats until hands are empty or `rounds` reached

Notes:
- The draft itself is a sub-loop — can be expressed as a flow `loop` with a `simultaneous`
  pick node. The mechanic may auto-wire this or reference an existing flow node.
- `alternating` pass direction is common in multi-round drafts (e.g., Sushi Go).
- Cards go directly to `draftTo` inventory (e.g., player hand or tableau), not to a
  discard pile.

Examples: Magic: The Gathering booster draft, Sushi Go, 7 Wonders, Blood Rage.

### `chaincraft:bounties`
**Status**: Not yet designed

A shared pool of objective cards (bounties) that award points or rewards to the first
player (or any player) who meets the objective condition.

Key config (tentative):
- `bountyType` — gamepiece type for bounty cards (forward ref)
- `bountyInventory` — where active bounties are displayed (game-scoped; mechanic owns
  unless other modules reference it)
- `condition` — how bounty completion is evaluated: `on-event` (triggered by a specific
  action) | `end-of-round` (checked at round end) | `end-of-game` (scored at game end)
- `claimStyle` — `first-only` (bounty removed when claimed) | `persistent` (multiple
  players can score same bounty at game end)
- `reward` — what happens on claim: property delta (score), effect ref, or both

Synthesizes:
- bounty display inventory (if not referenced elsewhere)
- claim check: wired to `condition` timing
- claim effect: applies `reward` and optionally removes bounty from active pool
- replenish trigger (optional): draw new bounty when one is claimed

Notes:
- `end-of-game` bounties with `claimStyle: persistent` are effectively scoring criteria
  — similar to Wingspan bonus cards or Catan longest road.
- `first-only` + `on-event` bounties are more like kill bounties or race objectives.
- Bounty conditions are expressed as JsonLogic evaluated against game/player state.

Examples: Wingspan bonus cards, Catan longest road/army, Clank! artifact objectives,
Ticket to Ride destination tickets.

### `chaincraft:status-effect`
**Status**: Not yet designed

Attaches a timed status to a gamepiece: an optional effect list that fires on each
turn/round boundary while active, with a duration after which the status auto-removes.

Key config (tentative):
- `id` — mechanic instance ID (allows multiple status types on the same game)
- `statusProperty` — piece property (boolean or integer) flagging the status is active;
  also used by action preconditions (e.g. gating an action while a piece is frozen/stunned)
- `tick` — effect list run each boundary while active (e.g. `update hp delta -1` for
  poison). Optional — omit for pure gating statuses (freeze, stun) that need no tick.
- `boundary` — `turn-start` | `turn-end` | `round-end` — when the tick fires and
  duration is decremented.
- `duration` — number of boundaries the status remains active, or `until-cleared` for
  indefinite (cleared manually via an `update` effect).
- `stacking` — policy when the same status is applied to a piece already carrying it:
  - `intensity` — accumulate magnitude (poison: each application adds to the tick damage)
  - `refresh` — reset duration to the new value, keep current magnitude
  - `extend` — add the new duration to the remaining duration
  - `ignore` — no-op if already active (burn: applied once, not stackable)

Synthesizes: duration counter property on the piece type, boundary-hook wiring for the
tick effect list, per-tick decrement and auto-removal when duration reaches zero.

**Depends on** a generic turn/round-boundary scheduling primitive (see Design notes below).
**Open**: stacking semantics are the hardest unresolved piece — in particular, ordering
when multiple statuses touch the same property (e.g. poison and regen both writing `hp`
on the same boundary). Decide before more than one status type coexists on a piece type.

Notes:
- Freeze/stun are the degenerate case: `tick` omitted, `duration: 1`, `stacking: refresh`.
  These can be modeled without this mechanic (boolean property + action precondition +
  turn-end `update` reset), but the mechanic unifies the pattern once the scheduler exists.
- Per-instance tracking: if a game has multiple piece instances carrying the same status,
  duration is tracked per piece, not globally.
- The `statusProperty` can be an integer to double as a stack counter (intensity stacking).

Examples: poison (DOT, `stacking: intensity`), burn (self-incrementing tick, `stacking:
ignore`), regeneration (heal-per-turn), temporary stat buffs/debuffs, stun/freeze (gating,
no tick).

## Design notes / open questions

- **Turn/round-boundary scheduling primitive**: Several mechanics need to wire effects
  to turn/round boundaries: `status-effect` (tick + duration decrement), `elimination`
  (per-player condition check), `score-track` (optional auto-advance). Rather than each
  mechanic reimplementing duration bookkeeping, a shared primitive is needed —
  `triggers: [{ on: 'turn-end' | 'turn-start' | 'round-end', nodeId?: string }]` — that
  mechanics can declare. This is the key prerequisite for `status-effect` and
  `elimination`; `score-track` can benefit too. Must be resolved before any of those
  mechanics are designed in detail.

- **Auto-wire vs explicit triggers**: Game-level mechanics that fire at turn/round
  boundaries (score-track advance, elimination check) could either auto-wire to the
  flow structure or require explicit `triggers: [{ on: "turn-complete", nodeId: ... }]`
  config. Auto-wire is simpler for LLMs; explicit is more composable.

- **Mechanic-owned vs referenced inventories**: If a mechanic exclusively owns an
  inventory, it should declare it inline — the LLM doesn't touch `inventories.ts`.
  If other modules reference it, it lives in `inventories.ts`.

- **Mechanic-owned piece types**: Same ownership principle applies to gamepiece types
  (e.g., score markers, charge tokens). If nothing else references them, the mechanic
  owns them.

- **Chaining mechanics**: `chaincraft:charges` wraps an `action` ID. That action could
  itself be a conversion. This composability should be tested/documented explicitly.

- **Custom mechanics**: `kind` strings are namespaced (`chaincraft:*` for built-ins,
  `mygame:*` for custom). Custom mechanics are a future extension point.
